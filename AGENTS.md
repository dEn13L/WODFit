- Логирование: AppLogger (core).
- Архитектура: Clean Architecture:

## 2. Продуктовая модель
Роли: coach (тренер), client (атлет). Клубов нет.
- Тренер ведёт тренировочные программы (programs): персональные (1 клиент) и групповые.
  Сущность «группа» УСТАРЕЛА и заменена на «программу» во всём проекте.
- Клиент вступает в программу по инвайт-коду (RPC join_program_by_code).
- Тренировка (workouts): идентификатор — дата и время (scheduled_at);
  опциональное уточнение сессии хранится в workouts.title и показывается
  в скобках после даты. Названия и описания тренировки в UI нет.
- Тренировка состоит из заданий (workout_parts): название + свободное описание + порядок.
- Атлет вносит результат (part_results) по каждому заданию; формат записи выбирает
  атлет (part_results.score_type); один пользователь — один результат на задание
  (UNIQUE(part_id, user_id)).
- Клиент видит результаты других участников своей программы; тренер — все результаты
  своих тренировок.
- Шаблоны тренировок — УДАЛЁННАЯ фича (legacy-таблицы в БД, кода нет).

## 3. Схема данных (актуальная)
profiles(id pk→auth.users, email, full_name, role user_role, created_at, updated_at)
programs(id, coach_id→profiles, name, kind program_kind, description null,
invite_code unique, created_at, updated_at)
program_members(program_id, user_id, joined_at; PK(program_id, user_id))
workouts(id, coach_id, title nullable — уточнение сессии, description nullable —
не используется, scheduled_at timestamptz, status workout_status,
created_at, updated_at)
workout_parts(id, workout_id, type nullable legacy, title, description, sort_order,
score_type nullable legacy, created_at)
workout_assignments(workout_id, program_id, assigned_at; PK(workout_id, program_id))
part_results(id, workout_id, part_id, user_id, status result_status,
score_type score_type — формат записи (fallback 'text'),
score_text, time_ms, rounds, reps, weight_kg, distance_m, calories,
note, client_updated_at, last_operation_id, deleted_at, created_at, updated_at;
UNIQUE(part_id, user_id))
legacy: workout_templates, workout_template_parts — таблицы сохранены, фича удалена,
код их не использует; новых зависимостей от них не создавать.

Enum'ы и подписи UI (строковые значения БД↔Dart живут в ЕДИНОМ маппере в core;
при добавлении значения обновляй маппер И миграцию одновременно):
- user_role: coach, client.
- program_kind: personal → «Персональная», group → «Группа».
- workout_status: draft → «Черновик», published → бейдж НЕ показывается.
- workout_part_type: legacy, в UI не выбирается и не заполняется;
  значения по sql/01: warmup, weightlifting, strength, crossfitComplex, cooldown,
  stretch, mobility; practice по истории добавлялся, но в миграциях его нет —
  наличие в живой БД не проверено.
- score_type: выбирается атлетом в форме ввода результата, хранится в
  part_results.score_type: none «Без фиксации (статус)», text «Текст (произвольно)»,
  time «Время», rounds_reps «Раунды + повторы», weight «Вес», reps «Повторы»,
  distance «Дистанция», calories «Калории».
- result_status: done «Выполнено», scaled «Масштабировано», notDone «Не выполнено».

RPC: join_program_by_code(p_invite_code text) — security definer, вступление по коду;
sync_part_result(...) — security invoker, идемпотентная LWW-синхронизация результатов.
RLS-принципы (не нарушать):
- тренер CRUD только свои programs/workouts и их детей;
- участник программы читает свою программу, назначенные published-тренировки,
  их задания и результаты участников своей программы;
- part_results: insert/update/delete только свои (user_id = auth.uid());
- тренер читает результаты своих тренировок;
- анонимный доступ запрещён ко всем таблицам;
- вступление в программу — только через RPC.
  Индексы существуют: programs(coach_id), program_members(program_id/user_id),
  workout_assignments(program_id/workout_id), part_results(workout_id/user_id),
  workouts(coach_id, scheduled_at).

## 4. Продуктовые правила интерфейса (СТРОГИЕ)
1.  Идентификатор тренировки — дата и время; уточнение сессии (workouts.title) —
    в скобках после даты в списках и в шапке клиента. Шапка тренерского экрана
    деталей — три строки: дата (formatDay), время (formatTime), уточнение.
    Описания тренировки в UI НЕ существует.
2.  Форматы дат — единый форматтер из core: списки «Сб, 19.09.2026, 19:00»;
    шапка клиента «Суббота, 19 сентября 2026, 19:00»;
    сегодня/завтра «Сегодня, 19:00» / «Завтра, 19:00».
3.  Структурная единица тренировки в UI — «задание» (код: WorkoutPart / workout_parts).
    Задание = название (bold) + описание (free text: в форме редактируется через
    боттом-шит, в просмотре показывается полным). Тип задания и формат результата
    в формах создания НЕ выбираются; workout_parts.type/score_type не заполняются.
4.  Формат записи результата выбирает атлет в форме ввода результата;
    хранится в part_results.score_type (fallback 'text').
5.  Счётчик заданий допустим только в заголовке секции «ЗАДАНИЯ ТРЕНИРОВКИ»
    экрана создания, с русской плюрализацией (1 задание / 2 задания / 5 заданий).
6.  Бейдж «Опубликовано» не существует. Бейдж «Черновик» (draft-семантика) —
    только для draft. У клиента бейджей статусов тренировки нет.
7.  Тренер НЕ вводит результаты: на тренерском экране деталей нет форм и кнопок
    ввода результата. Просмотр — кнопка «Результаты участников» внизу экрана.
8.  Номера и счётчики заданий запрещены вне правила 5: никаких «Задание N»,
    «Частей: N», «(2)». Идентификатор задания в UI — его название;
    бейджей типа задания не существует.
9.  Результаты и тайминги отображаются моноширинным шрифтом.
10. Терминология UI (без синонимов): «программа», «участник/атлеты», «тренировка»,
    «задание», «результат». Запрещены в UI-текстах: «группа», «блок», «часть»,
    «шаблон».
11. Кнопки «Создать на основе» / «Из существующей» НЕ СУЩЕСТВУЮТ.
    Создание тренировки: пустая форма либо с предвыбранной программой
    (параметры initialProgramId/initialProgramIds).
12. Все списки и детали обязаны иметь состояния: loading (skeleton/indicator),
    empty с полезным текстом и действием, error с «Повторить».
13. Удаления (программа, тренировка, участник, результат, задание) — только через
    ConfirmDialog. Успех/ошибка операций — SnackBar.
14. Единая глобальная система тем: тёмная (дефолт) и светлая, переключение через
    ThemeCubit с персистентностью в Hive-боксе settings_box (ключ theme_mode).
    ВСЕ экраны, диалоги и bottom sheet'ы следуют глобальной теме.
    Изолированные локальные темы и обёртки Theme(data: ...) ЗАПРЕЩЕНЫ.
    Цвета в виджетах — только через Theme.of(context): colorScheme, cardTheme,
    textTheme, dividerColor, AppThemeExtension. Захардкоженные hex-литералы и
    прямые ссылки AppColors.dark*/AppColors.light* внутри lib/presentation ЗАПРЕЩЕНЫ.
15. Семантические цвета (через AppThemeExtension): destructive/publish #EF4444;
    draft/warning — amber; success — green. Primary-экшен: тёмная тема —
    лайм #CCFF00 с чёрным текстом, светлая — циан #06B6D4 с белым текстом
    (через colorScheme.primary).
16. Веб: контент до 1200 px, сводки результатов — таблицей на широких экранах.
17. Фича «Шаблоны тренировок» УДАЛЕНА: экранов, роутов, кнопок и репозиториев
    шаблонов не существует; legacy-таблицы БД сохранены.
18. Категории матрицы выполнения: «Выполнил» — есть результат по каждому заданию
    и ни у одного нет статуса notDone; «Частично» — есть хотя бы один результат,
    но заполнены не все задания либо присутствует notDone; «Не заполнил» — нет
    ни одного результата.

## 5. Правила кода
- presentation НЕ импортирует supabase_flutter: все запросы через репозитории
  data-слоя за интерфейсами из domain.
- Экран = свой Cubit/Bloc; состояние — sealed/enum-статусы (initial/loading/loaded/error).
- Ошибки Supabase ловить явно: AuthException, PostgrestException (логировать message,
  details, hint, code через AppLogger), показывать пользователю понятным текстом.
  Молчаливых catch не должно быть вообще.
- Списки с данными из нескольких таблиц брать одним запросом и джойнить в памяти;
  N+1-запросы запрещены.
- Deprecated API не использовать: вместо withOpacity — withValues(alpha:).
- Идентификаторы кода — английские; UI-строки — русские; комментарии — русские допустимы.
- Не рефакторить код вне задачи. Не переписывать целые файлы без необходимости:
  точечные правки. Крупные виджеты выносить в отдельные файлы.
- Любое изменение схемы БД = файл миграции sql/NN_slug.sql (следующий номер)
  ПЛЮС тот же SQL в ответе. Переименования — через ALTER ... RENAME
  (сохранение данных), не пересозданием таблиц.
- После переименований сущностей обновлять ВСЕ места: модели, репозитории, cubit,
  экраны, роуты, тексты, empty-состояния.
- Маршруты по существующим паттернам app_router.dart: /coach/..., /client/...;
  ролевая изоляция маршрутов обязательна.

- Offline-first сохранение результатов использует `result_sync_box`: операции
  create/update/delete имеют UUID, сохраняются между перезапусками, повторяются
  с exponential backoff и удаляются только после подтверждения Supabase. Конфликты
  разрешаются по LWW (`client_updated_at`, затем UUID операции); UI различает
  серверное подтверждение, локальное ожидание и ошибку синхронизации.
- Миграция `sql/08_offline_result_sync.sql` применена к живой БД: добавлены
  метаданные LWW, soft delete и идемпотентный RPC `sync_part_result`.

Агент работает с репозиторием напрямую: правит файлы, коммитит в рабочую ветку, пушит.
1. Небольшая задача (≤ 6 файлов, без схемы БД) — выполнять сразу целиком.
2. Крупная задача (> 6 файлов), изменение схемы БД или неочевидное продуктовое
   решение — сначала план (3–7 пунктов, разбивка на шаги), дождаться подтверждения,
   затем выполнять шаги подряд (коммит на шаг).
3. Итоговый ответ, без воды:
   - Сделано: 3–7 пунктов, только суть.
   - Файлы: список созданных/изменённых.
   - SQL: если менялась схема — путь к миграции и тот же текст в ответе
     (применяется вручную).
   - Проверка: результат flutter analyze + чек-лист ручной проверки 5–12 шагов.
   - Заметки: допущения, риски, противоречия с этим документом (если задача ему
     противоречит — выполнить и указать противоречие одной строкой).
Запрещено: код в ответе (он в коммите), вступление «конечно!», пересказ контекста,
резюме прошлых шагов, предложения «давайте также сделаем…» вне задачи.

## 10. Экономия контекста
- Открывать только файлы, которых касается задача; не сканировать проект целиком.
- Между шагами не пересказывать предыдущие: только дельта.
- Если данных не хватает: сделать минимальное безопасное допущение и указать его
  в «Заметках». Вопросы задавать только если без ответа есть риск потери данных,
  поломки схемы БД или продуктовое решение за владельцем.

## 11. Правило поддержки этого документа
После каждого завершённого шага разработки раздел 6 (базис) и раздел 7
(приоритеты) обновляются под фактическое состояние. Раздел 4 меняется только
явным продуктовым решением заказчика. Раздел 3 меняется одновременно с применением
миграции. Несовпадение документа с кодом — ошибка документа, чинится правкой
документа, а не молчаливым игнорированием. Агент обновляет документ в том же
коммите/PR, что и изменения кода.
