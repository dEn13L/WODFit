## 1. Паспорт проекта
- Продукт: WOD Fit — приложение кроссфит-тренировок для тренера и атлетов.
- Клиент: Flutter (Dart), таргеты Android / iOS / Web (адаптив).
- Состояние: flutter_bloc. Навигация: go_router.
- Бэкенд: Supabase (PostgreSQL, Auth, RLS, RPC, Storage не используется).
- Локально: Hive — ТОЛЬКО кэш (профиль/сессия, кэш тренировок, очередь результатов).
  Источник истины — Supabase. Никогда не строй бизнес-логику на Hive.
- Логирование: AppLogger (core).
- Архитектура: Clean Architecture.
  lib/core (router, theme, config, errors, utils, logger),
  lib/domain (entities, repositories-интерфейсы),
  lib/data (models, datasources, repositories-реализации),
  lib/presentation (screens, widgets, bloc/cubit).
- Зависимости текущего стека: flutter_bloc, go_router, supabase_flutter, hive/hive_flutter,
  intl, uuid, equatable. Новые зависимости — только с явным обоснованием в ответе.
- freezed/json_serializable НЕ использовать: модели — обычные Dart-классы
  с fromJson / toJson / toDb.
- Переменные окружения: SUPABASE_URL, SUPABASE_ANON_KEY через --dart-define.
  service_role key в клиенте запрещён навсегда.

## 2. Продуктовая модель
Роли: coach (тренер), client (атлет). Клубов нет.
- Тренер ведёт тренировочные программы (programs): персональные (1 клиент) и групповые.
  Сущность «группа» УСТАРЕЛА и заменена на «программу» во всём проекте.
- Клиент вступает в программу по инвайт-коду (RPC join_program_by_code).
- Тренер создаёт тренировки (workouts) из блоков (workout_parts), назначает их программам
  (workout_assignments), публикует (status published) или держит черновиком (draft).
- Тренировка НЕ имеет названия: её идентификатор — дата и время (scheduled_at).
- Шаблоны (workout_templates + workout_template_parts) ИМЕЮТ имя — это записи библиотеки.
  При развёртывании шаблона имя в тренировку НЕ копируется.
- Клиент вносит результат (part_results) по каждому блоку тренировки;
  один пользователь — один результат на блок (UNIQUE(part_id, user_id)).
- Клиент видит результаты других участников своей программы; тренер — все результаты
  своих тренировок.

## 3. Схема данных (актуальная)
profiles(id pk→auth.users, email, full_name, role user_role, created_at, updated_at)
programs(id, coach_id→profiles, name, kind program_kind, description null,
invite_code unique, created_at, updated_at)
program_members(program_id, user_id, joined_at; PK(program_id, user_id))
workouts(id, coach_id, title nullable НЕ ИСПОЛЬЗУЕТСЯ, description, scheduled_at timestamptz,
status workout_status, created_at, updated_at)
workout_parts(id, workout_id, type workout_part_type, title, description, sort_order,
score_type score_type, created_at)
workout_assignments(workout_id, program_id, assigned_at; PK(workout_id, program_id))
part_results(id, workout_id, part_id, user_id, status result_status, score_text, time_ms,
rounds, reps, weight_kg, distance_m, calories, note, created_at, updated_at;
UNIQUE(part_id, user_id))
workout_templates(id, coach_id, name, description, created_at, updated_at)
workout_template_parts(id, template_id, type, title, description, sort_order, score_type)

Enum'ы и подписи UI (точные строковые значения БД↔Dart живут в ЕДИНОМ маппере в core;
при добавлении значения обновляй маппер И миграцию одновременно):
- user_role: coach, client.
- program_kind: personal → «Персональная», group → «Группа».
- workout_status: draft → «Черновик», published → бейдж НЕ показывается.
- workout_part_type (порядок в списках выбора):
  warmup «Разминка», practice «Практика», weightlifting «Тяжёлая атлетика»,
  strength «Сила», crossfit complex «Комплекс (WOD)», cooldown «Заминка»,
  stretch «Растяжка», mobility «Мобилити».
- score_type: none «Без фиксации (статус)», text «Текст (произвольно)», time «Время»,
  rounds_reps «Раунды + повторы», weight «Вес», reps «Повторы»,
  distance «Дистанция», calories «Калории».
- result_status: done «Выполнено», scaled «Масштабировано», notDone «Не выполнено».

RPC: join_program_by_code(p_invite_code text) — security definer, вступление по коду.
RLS-принципы (не нарушать):
- тренер CRUD только свои programs/workouts/templates и их детей;
- участник программы читает свою программу, назначенные published-тренировки,
  их части и результаты участников своей программы;
- part_results: insert/update/delete только свои (user_id = auth.uid());
- тренер читает результаты своих тренировок;
- анонимный доступ запрещён ко всем таблицам;
- вступление в программу — только через RPC.
  Индексы существуют: programs(coach_id), program_members(program_id/user_id),
  workout_assignments(program_id/workout_id), part_results(workout_id/user_id),
  workouts(coach_id, scheduled_at).

## 4. Продуктовые правила интерфейса (СТРОГИЕ)
1. Идентификатор тренировки — дата и время; опциональное уточнение сессии
   (workouts.title) показывается в скобках после даты. Описание тренировки
   в UI НЕ существует.
2. Форматы дат — единый форматтер из core с параметром уточнения:
   списки: "Сб, 19.09.2026, 19:00"; шапки деталей: "Суббота, 19 сентября 2026, 19:00";
   сегодня/завтра: "Сегодня, 19:00" / "Завтра, 19:00".
3. Структурная единица тренировки в UI — «задание» (код: WorkoutPart /
   workout_parts). Задание = название (bold, инлайн) + описание (free text,
   в форме редактируется через боттом-шит, в просмотре показывается полным).
   Типы блоков и форматы результатов в формах создания НЕ выбираются;
   type/score_type в workout_parts не заполняются.
3bis. Формат записи результата выбирает атлет в форме ввода результата;
      хранится в part_results.score_type (fallback 'text').
3ter. Счётчик заданий допустим только в заголовке секции «ЗАДАНИЯ ТРЕНИРОВКИ»
      экрана создания, с русской плюрализацией.
4. Бейдж «Опубликовано» не существует. Бейдж «Черновик» (amber) — только для draft.
   У клиента бейджей статусов нет.
4quater. Тренер НЕ вводит результаты тренировок: на тренерском экране
   деталей нет форм и кнопок ввода результата. Ввод результата —
   только клиентский флоу. Просмотр результатов тренера — через
   кнопку «Результаты участников» внизу экрана деталей.
5. Номера и счётчики блоков запрещены: никаких «Часть N», «Частей: N», «(2)».
   Идентификатор блока в UI — бейдж типа блока. Порядок блоков — только sort_order
   и стрелки ↑↓ в редактировании.
6. Результаты и тайминги отображаются моноширинным шрифтом.
7. Терминология UI (без синонимов): «программа», «участник/атлеты», «тренировка»,
   «блок/часть тренировки», «шаблон», «результат». Слово «группа» в UI-текстах запрещено.
8. Кнопки «Создать на основе» / «Из существующей» НЕ СУЩЕСТВУЮТ и не добавляются.
   Создание тренировки: пусто, из шаблона, либо с предвыбранной программой
   (параметры initialProgramId/initialProgramIds формы).
9. Все списки и детали обязаны иметь состояния: loading (skeleton/indicator),
   empty с полезным текстом и действием, error с «Повторить».
10. Удаления (программа, тренировка, шаблон, участник, результат, блок) — только через
   ConfirmDialog. Успех/ошибка операций — SnackBar.
11. Тёмная спортивная тема, токены:
    фон #0C0F12, поверхность #171C21, поля #10151A, контур #2A3138,
    акцент лайм #C6F432 (текст на нём #0C0F12), текст #F2F5F7,
    вторичный #98A2AD, success #34D399, draft #F59E0B, danger #F43F5E.
    Скругления: карточка 20, поле 14, бейдж 10, кнопки pill.
    Заголовки Manrope 700–800, цифры результатов — mono.
12. Тёмная тема — дефолт приложения, КРОМЕ CreateWorkoutScreen и тренерского
    WorkoutDetailScreen: оба используют локальную светлую тему
    workoutFormTheme. Клиентские экраны остаются тёмными до решения
    о полном редизайне.
13. Веб: контент до 1200 px, сводки результатов — таблицей на широких экранах.
14. Фича «Шаблоны тренировок» УДАЛЕНА из приложения: экранов, роутов,
    кнопок и репозиториев шаблонов не существует. Таблицы БД сохранены.

## 5. Правила кода
- presentation НЕ импортирует supabase_flutter: все запросы через репозитории data-слоя
  за интерфейсами из domain.
- Экран = свой Cubit/Bloc; состояние — sealed/enum-статусы (initial/loading/loaded/error).
- Ошибки Supabase ловить явно: AuthException, PostgrestException (логировать message,
  details, hint, code через AppLogger), показывать пользователю понятным текстом.
  Молчаливых catch не должно быть вообще.
- Идентификаторы кода — английские; UI-строки — русские; комментарии — русские допустимы.
- Не рефакторить код вне задачи. Не переписывать целые файлы без необходимости:
  точечные правки. Крупные виджеты выносить в отдельные файлы.
- Любое изменение схемы БД = файл миграции supabase/migrations/NNN_slug.sql
  ПЛЮС тот же SQL в ответе. Переименования делать через ALTER ... RENAME (сохранение данных),
  не пересозданием таблиц.
- После переименований сущностей обновлять ВСЕ места: модели, репозитории, cubit, экраны,
  роуты, тексты, empty-состояния.
- Маршруты по существующим паттернам app_router.dart: /coach/..., /client/...;
  ролевая изоляция маршрутов обязательна.
