# WOD Fit — инструкции агента

## Context
Краткий действующий контракт. Перед правкой прочитай
релевантные документы через [индекс](docs/agent/README.md); ссылки НЕ загружают их
автоматически. Читай точечно; не считай неоткрытое известным. История не даёт текущих разрешений.

## Permissions
- В рамках разрешённой задачи автономно: feature-ветка, код/документация, тесты,
  commit, push feature-ветки в dEn13L/WODFit, создание PR — без лишних подтверждений.
  Read-only/plan-only/«не commit/push/PR» задачи важнее общей автономии.
- Сложную задачу планируй (3–7 шагов), затем выполняй; порог >6 файлов НЕ требует
  повторного одобрения уже разрешённой работы. Неочевидное продуктовое решение,
  риск потери данных или поломки схемы — вопрос владельцу до действия.
- Только по отдельной прямой команде: push в main, merge, force push, deploy,
  применение live миграций/любая live запись, изменение secrets или repo settings.
  Push main запускает deploy; работа — feature-ветка и PR.
- Секреты НИКОГДА не раскрывать и не коммитить даже при одобрении; service_role
  в клиенте запрещён. Не печатать credentials в ответах/логах. Настройка секретов
  возможна лишь безопасным закрытым механизмом по прямой задаче.
- Несколько пишущих агентов: отдельные worktree или сериализованные записи;
  не править совместно одну checkout и не затирать чужие изменения.
- Не рефакторить вне задачи; точечные изменения, крупные виджеты отдельно.
  Безрисковое допущение обозначить.

## Engineering
- Flutter/Dart Android/iOS/Web; flutter_bloc, go_router; Supabase PostgreSQL/Auth/RLS/RPC,
  Storage не используется. Clean Architecture: core; domain (entities/interfaces);
  data (models/datasources/implementations); presentation (screens/widgets/Bloc).
- presentation НЕ импортирует supabase_flutter; запросы через data repositories за
  domain interfaces. Экран = свой Cubit/Bloc, sealed/enum initial/loading/loaded/error.
- Hive: settings_box — тема; workouts_box — черновик формы; result_sync_box —
  результаты/очередь. После server ack источник истины Supabase. Offline операции
  UUID, LWW (client_updated_at, затем UUID), backoff; очередь удалять только после ack,
  изолировать аккаунты; различать pending/error/confirmed.
- Модели обычные Dart fromJson/toJson/toDb; freezed/json_serializable не использовать.
  Новые зависимости — с явным обоснованием. Английский код, русский UI;
  русские комментарии допустимы. withValues(alpha:), не deprecated withOpacity.
- AuthException/PostgrestException обрабатывать явно; AppLogger message/details/hint/code
  и понятная ошибка пользователю, без молчаливых catch и без раскрытия секретов.
  Локальный журнал маскирован, без автоматической отправки на сервер.
- Многотабличные списки: один запрос и join в памяти, не N+1. Переименования обновлять
  во всех моделях/repositories/cubit/screens/routes/текстах/empty состояниях.
  /coach/... и /client/... по app_router.dart, обязательная ролевая изоляция.
- SUPABASE_URL/SUPABASE_ANON_KEY через --dart-define; см. [архитектуру](docs/agent/architecture.md).

## Database
- Роли coach/client, без клубов; программы personal/group, не отдельная сущность «группа».
  Инвайт только join_program_by_code. UNIQUE(part_id,user_id), формат выбирает атлет.
- RLS: тренер CRUD только свои programs/workouts и детей, читает их результаты.
  Участник читает свою программу, назначенные published тренировки/задания и
  результаты участников общей назначенной программы. Свои исторические результаты
  остаются читаемыми. Anonymous доступ к таблицам запрещён.
- part_results insert/update/delete только свои user_id=auth.uid(), только client в
  назначенной published тренировке; part_id/workout_id связаны составным FK.
  profiles только связанные пользователи; у клиента UPDATE лишь своего full_name,
  id/email/role неизменяемы. authenticated не имеет прямого INSERT program_members;
  участник удаляет только своё членство, тренер исключает лишь из своих программ.
- Helpers RLS в private, безопасный search_path, минимальные grants; прямой EXECUTE
  set_workout_published_at закрыт, trigger сохраняется. Не ослаблять security invoker
  save_workout/sync_part_result; join_program_by_code — security definer.
- Сохранение workout/parts/assignments атомарно; неизменённые ID/assigned_at сохранять.
  Задание с любыми результатами, включая tombstone, отдельно не удалять; каскад
  удаления целой тренировки сохраняется, отказ БД восстанавливает задания/UUID в форме.
- Enum ↔ Dart в едином core-маппере: новое значение = mapper + миграция одновременно.
  Изменение схемы = следующий sql/NN_slug.sql + тот же SQL в итоговом ответе;
  переименование ALTER ... RENAME без потери данных. Проверять live read-only перед
  схемой; наличие SQL не доказывает применение. Индексы — после EXPLAIN.
  Статусы 14/15 противоречивы/неизвестны: [реестр](docs/agent/live-db-status.md),
  [схема/enum/RLS](docs/agent/database-contract.md).

## UI-contract
1.  Название «Тренировка N» — автоматический стабильный номер внутри программы.
  Дата/время показываются отдельно. В контексте программы — её номер;
  в общем списке/деталях при нескольких программах — пары программа/номер.
  Уточнения сессии и поля названия в форме нет. До подтверждения поддержки
  нумерации БД UI показывает «Тренировка»; live статус — docs/agent/live-db-status.md.
2.  Форматы дат — единый форматтер из core: списки «Сб, 19.09.2026, 19:00»;
  шапка клиента «Суббота, 19 сентября 2026, 19:00»;
  сегодня/завтра «Сегодня, 19:00» / «Завтра, 19:00».
3.  Структурная единица тренировки в UI — «задание» (код: WorkoutPart / workout_parts).
  Задание = название (bold) + описание (free text: оба поля редактируются
  прямо в карточке, в просмотре показывается полным). Тип задания и формат результата
  в формах создания НЕ выбираются; workout_parts.type/score_type не заполняются.
4.  Формат записи результата выбирает атлет в форме ввода результата;
  хранится в part_results.score_type (fallback 'text').
5.  Счётчик заданий допустим только в заголовке секции «ЗАДАНИЯ ТРЕНИРОВКИ»
  экрана создания, с русской плюрализацией (1 задание / 2 задания / 5 заданий).
6.  Бейдж «Опубликовано» не существует. Бейдж «Черновик» (draft-семантика) —
  только для draft. У клиента бейджей статусов тренировки нет.
7.  Тренер НЕ вводит результаты: на тренерском экране деталей нет форм и кнопок
  ввода результата. Просмотр — кнопка «Результаты участников» внизу экрана.
8.  Номера и счётчики заданий запрещены вне правила 5: никаких «Задание N»,
  «Частей: N», «(2)». Идентификатор задания в UI — его название;
  бейджей типа задания не существует.
9.  Результаты и тайминги отображаются моноширинным шрифтом.
10. Терминология UI (без синонимов): «программа», «участник/атлеты», «тренировка»,
  «задание», «результат». Запрещены в UI-текстах: «группа», «блок», «часть»,
  «шаблон».
11. Кнопки «Создать на основе» / «Из существующей» НЕ СУЩЕСТВУЮТ.
  Создание тренировки: пустая форма либо с предвыбранной программой
  (параметры initialProgramId/initialProgramIds).
12. Все списки и детали обязаны иметь состояния: loading (skeleton/indicator),
  empty с полезным текстом и действием, error с «Повторить».
13. Удаления (программа, тренировка, участник, результат, задание) — только через
  ConfirmDialog. Исключение: задание с пустыми после trim названием и описанием
  удаляется из формы без подтверждения. Успех/ошибка операций — SnackBar.
14. Единая глобальная система тем: тёмная (дефолт) и светлая, переключение через
  ThemeCubit с персистентностью в Hive-боксе settings_box (ключ theme_mode).
  ВСЕ экраны, диалоги и bottom sheet'ы следуют глобальной теме.
  Изолированные локальные темы и обёртки Theme(data: ...) ЗАПРЕЩЕНЫ.
  Цвета в виджетах — только через Theme.of(context): colorScheme, cardTheme,
  textTheme, dividerColor, AppThemeExtension. Захардкоженные hex-литералы и
  прямые ссылки AppColors.dark*/AppColors.light* внутри lib/presentation ЗАПРЕЩЕНЫ.
15. Семантические цвета (через AppThemeExtension): destructive #EF4444; публикация — colorScheme.primary;
  draft/warning — amber; success — green. Primary-экшен: тёмная тема —
  циан #22D3EE с текстом #082F49, светлая — циан #0E7490 с белым текстом
  (через colorScheme.primary).
16. Веб: контент до 1200 px, сводки результатов — таблицей на широких экранах.
17. Фича «Шаблоны тренировок» УДАЛЕНА: экранов, роутов, кнопок и репозиториев
  шаблонов не существует; legacy-таблицы БД сохранены.
18. Категории матрицы выполнения: «Выполнил» — есть результат по каждому заданию
  и ни у одного нет статуса notDone; «Частично» — есть хотя бы один результат,
  но заполнены не все задания либо присутствует notDone; «Не заполнил» — нет
  ни одного результата.


## Restricted-features
Без отдельной прямой задачи: таймер, лидерборды, платежи, видео/пользовательские
изображения, push-уведомления, HealthKit/Google Fit/wearables, клубы/абонементы, AI, CSV,
«создание из существующей», воскрешение шаблонов, новые сущности сверх
[контракта БД](docs/agent/database-contract.md). Исключение — согласованная встроенная
декоративная графика; разрешено публиковать согласованные спортивные иллюстрации
из предоставленных владельцем фотографий вместе с кодом в публичном репозитории.

## Verification-and-maintenance
- До каждого commit: чистый `flutter analyze`. До готовности PR: format,
  `git diff --check`, test, web build; SQL checks при связанных изменениях.
  Docs-only: docs checker + analyze + diff; блокеры не считать успехом.
- PR CI без deploy; проверять workflows. Не устанавливать SDK/запускать hook по истории.
- Итог: сделано, файлы, реальные проверки, manual checklist (5–12 шагов при UI),
  SQL при схеме, риски. Без кода кроме SQL, без пересказа прошлых шагов.
- В том же PR обновлять тематический статус/очередь, а не копить историю здесь.
  UI нормы — только по явному продуктовому решению; live факты — с доказательством.
  Несовпадения исправлять явно; код не отменяет продуктовые/security инварианты.
  Архив/точные source блоки неизменяемы; новые сведения вне них.
