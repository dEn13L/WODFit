## Порядок применения для окружений, где 12/13 ещё не применены

В production wod-fit эти шаги уже выполнены владельцем. Повторно применять
миграции ради проверки не требуется; использовать read-only postflight.

1. Проверить project ref и production commit; проверить актуальность main и live.
2. Выполнить docs/12_security_hardening_preflight.sql, сохранить все результаты.
   При несоответствии part/workout, неизвестных score_type, владельцах не-coach
   или неожиданных зависимостях не применять миграции; не удалять и не исправлять
   пользовательские данные автоматически.
3. Вручную применить sql/12_harden_result_and_profile_access.sql по отдельной
   прямой команде владельца. Затем применить sql/13_result_integrity.sql.
   Обе транзакционные; lock_timeout 5s, statement_timeout 60s. При timeout
   транзакция откатывается; выбрать другое окно, не увеличивать timeout вслепую.
4. Выполнить docs/security-hardening-postflight.sql. Все строки checks — PASS.
   Дополнительно сверить полные тела функций, USING/WITH CHECK и default ACL.
   Схема private должна отсутствовать в Data API exposed schemas.
5. Выполнить read-only матрицу ниже с заранее известными тестовыми связями.
6. Выполнить функциональный smoke на тестовом окружении или в отдельно
   согласованном production-сценарии. Зафиксировать ожидаемое/фактическое и
   обезличенные доказательства. Только после этого обновлять статус завершения.

12 не выдаёт доступ к legacy-таблицам, переводит их политики на authenticated,
закрывает смену role/email/id через UPDATE профиля, оставляя UPDATE full_name.
Новые SECURITY DEFINER helpers используют текущий auth.uid() и profiles.role;
рекурсивные проверки читают отношения под владельцем функции.
13 сохраняет параметр p_score_type TEXT у SECURITY INVOKER RPC, приводит его к enum.
Существующие nullable score_type сохраняются. Составной FK заменяет одиночную
связь результата с заданием; каскадное удаление сохраняется, перенос задания
с существующими результатами в другую тренировку запрещён.

Новые функции/таблицы postgres требуют явных grants: default privileges
не должны автоматически открывать новые объекты anon/authenticated.
У существующего клиента имена RPC-параметров не меняются:
join_program_by_code(code TEXT), sync_part_result(..., p_score_type TEXT, ...).
Регистрация с выбором coach/client остаётся продуктовым поведением; роль при
последующей авторизации берётся из profiles, а не из редактируемого JWT metadata.

## Read-only матрица

Использовать реальные JWT тестовых пользователей через Data API GET/HEAD
или отдельную READ ONLY SQL-транзакцию на каждую роль. SQL role simulation
не заменяет API-проверку. Проверить current_user и auth.uid() до запросов.
Не использовать service_role для доказательства RLS.

| Сценарий | Ожидаемый результат |
|---|---|
| Coach A: программы, состав, свои draft/published, задания, результаты | Все свои данные доступны |
| Client A1: состав A с A2 без результатов | Оба участника присутствуют |
| Client A1: published и draft A | Published доступна; draft отсутствует |
| Client A1: одна тренировка назначена A и B | Не видит результаты и участников B без общего членства |
| Client B/Coach B: известные чужие IDs | Защищённых строк нет |
| Профили | Только свой, связанные участники/тренер; coach также видит авторов результатов своих тренировок |
| anon: основные и legacy-таблицы | Отказ по правам |
| Вложенные SELECT клиента | programs/members/profiles/assignments/results не теряют доступные связи |

Собственные исторические результаты остаются читаемыми после выхода, но запись
результатов требует актуального членства и published-тренировки. После выхода
pending offline-операции могут получать отказ; очередь не удалять автоматически.

Открытие клиентом деталей тренировки записывает workout_views. Загрузка своих
результатов запускает synchronize() и может отправить локальную очередь.
Для строго read-only UI использовать отдельную чистую сессию с блокировкой
изменяющих Data API/RPC-запросов; заблокированный запрос отмечать отдельно,
не считать его серверной ошибкой. Полный UI smoke включает эти записи и
не может считаться read-only.

## Функциональный smoke и завершение

1. Client вступает по валидному коду, включая пробелы/другой регистр; повтор идемпотентен.
2. Неверный код показывает понятный русский текст без code/details/hint; fallback INSERT отсутствует.
3. Coach, пользователь без profile и anon не вступают; прямой membership INSERT закрыт.
4. Client выходит только сам; coach исключает только из своей программы.
5. Coach создаёт/публикует тренировку; publication trigger работает без прямого EXECUTE.
6. Client сохраняет, изменяет, удаляет свой результат; RPC повтор и stale LWW не портят запись.
7. Чужой результат, draft, неназначенная тренировка, неверная пара part/workout отклоняются.
8. Изменение role/email профиля отклоняется; full_name собственного профиля изменяется.
9. Offline очередь восстанавливается после перезапуска; подтверждение сервера меняет sync status.
10. Вход/выход и матрица результатов проверены на mobile Web и широком экране.

Готовность к merge: Flutter analyze/test/build и SQL job зелёные.
Готовность hardening в production: 12/13 применены, postflight PASS, private не
экспонируется, read-only и функциональные smoke пройдены с доказательствами.
До этого не отмечать production hardening завершённым.
