## Исправление формы для iPhone Safari (27 октября 2026)

База: main `356b93f`. Верхние действия адаптированы к ширине и масштабу текста:
компактная кнопка черновика с tooltip, ограниченная ширина публикации и адаптивная
высота панели. Дата/время на узком экране идут вертикально, счётчик заданий
переносится, длинное название программы ограничено доступной шириной. Форма
учитывает SafeArea. Описание задания использует 16 px для предотвращения
автоприближения Safari. HTML получает высоту 100dvh: Flutter 3.47.5 на iOS
измеряет documentElement.clientHeight, поэтому высота должна учитывать панели
браузера. Данных, схемы БД и зависимостей изменения не касаются.

Регрессионные widget-тесты покрывают обе темы, 320/390/480 px, масштаб 1/1.5,
ландшафт 844×390, длинные тексты, клавиатуру, доступность публикации/черновика
и добавление задания над нижним отступом. Эти тесты не воспроизводят интерфейс
самого Safari; перед выпуском нужна проверка на реальном iPhone:

1. В обеих темах открыть создание тренировки с развёрнутыми панелями Safari.
2. Убедиться, что публикация и кнопка черновика доступны; сохранить черновик.
3. Ввести длинные название и описание задания: поля не уходят вправо,
   фокус не вызывает автоприближение.
4. Скрыть клавиатуру, прокрутить вниз, свернуть/развернуть панели Safari
   и добавить ещё одно задание.
5. Повернуть iPhone, повторить ввод и добавление; проверить увеличенный текст
   и редактирование существующей тренировки.

Локальная проверка: dart format, чистый flutter analyze, 182 проходящих теста,
release web build (включая Wasm dry run), docs checker и git diff --check.
Реальный iPhone/Safari в этой среде недоступен; пункты выше остаются ручной проверкой.

## Повторное исправление перекрытия браузерными панелями (28 октября 2026)

PR #33 слит в main `0e5b598`, workflow deploy 40528379852 завершился успешно.
Скриншот владельца подтверждает, что проблема оставалась. Предположение предыдущего
исправления о влиянии 100dvh на documentElement.clientHeight оказалось неверным:
в standards mode clientHeight корневого элемента возвращает высоту viewport.
В браузерной проверке при видимой области y=47, height=664 и clientHeight=844
Flutter продолжал создавать полноразмерную поверхность 844 px.

Теперь BrowserViewport подключён над Navigator в MaterialApp.builder для всего
веб-приложения: маршрутов создания/редактирования, деталей, верхних/нижних панелей
и диалогов. Он читает VisualViewport и слушает resize/scroll, ограничивает интерфейс
видимым прямоугольником и корректирует MediaQuery. Браузерные отступы отделены от
клавиатуры, чтобы Scaffold и bottom sheet не вычитали её высоту дважды. Нормальное
full-page embedding Flutter сохранено; у custom DOM embedding в текущем SDK
keyboard insets всегда нулевые. Pinch zoom сохраняет последнюю компоновку; native
Android/iOS используют исходные метрики Flutter и не получают веб-обёртку.
Фон свободных областей берётся из глобальной темы. Новых зависимостей/SQL нет.

Проверки включают обе темы, увеличенный текст, ширину 320 px, видимые верхнюю и
нижнюю кнопки, диалог, смещение viewport при клавиатуре, восстановление размеров
и поворот экрана. Локальный Chromium с моделированием iPhone VisualViewport
проверяет настоящий Flutter и доступность кнопок; это не проверка WebKit/Safari
на физическом устройстве.

Перед выпуском на устройстве владельца:
1. В обычной вкладке открыть детали и редактирование тренировки: верхние кнопки
   должны быть ниже панели браузера, нижние — выше адресной панели.
2. Свернуть/развернуть панели прокруткой и снова проверить обе границы.
3. Ввести длинное описание с открытой клавиатурой, затем закрыть её.
4. Повернуть экран, проверить увеличенный текст и обе глобальные темы.
5. Проверить диалог/нижнюю форму результата, повторный вход на страницу и запуск
   через иконку главного экрана, если этот способ используется.

Проверено локально: dart format, flutter analyze без замечаний, 185 проходящих
тестов, release web build с успешным Wasm dry run, docs checker и diff --check.
Chromium smoke прошёл в обеих темах: верхняя/нижняя кнопки, клавиатура,
